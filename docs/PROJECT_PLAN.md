# XTodoY 项目规划

> 版本：v0.1（规划稿） · 日期：2026-11-02 · 仓库：https://github.com/AhDaii/XTodoY.git

---

## 1. 项目概述

XTodoY 是一款面向 PC 桌面端的待办事项管理软件，主打 **轻量常驻、按时提醒、多级标签分类、完成统计**。

### 1.1 核心功能范围

| 编号 | 功能模块 | 说明 |
|---|---|---|
| F1 | 待办管理 | 新建 / 编辑 / 删除待办；每项前有单选框（圆形勾选框），用户手动勾选完成 / 取消完成 |
| F2 | 时间与循环 | 设置事项日期/时间（可仅日期、可全天）；循环规则：每天 / 每周（指定星期）/ 每月（指定日）/ 每年 / 自定义间隔 |
| F3 | 提醒 | 每个事项可设置一个或多个提醒时间（准时、提前 N 分钟/小时/天、自定义时间点）；默认通过系统通知渠道（Windows Toast / macOS 通知中心 / Linux libnotify）推送；支持稍后提醒 |
| F4 | 标签 | 待办可挂多个标签；标签支持多级（父子树）；按标签分类浏览，选中父标签时包含子标签事项 |
| F5 | 标签管理 | 标签的增删改、重命名、颜色、拖拽排序与调整层级、合并、删除时处理关联事项 |
| F6 | 后台常驻 | 关闭主窗口后最小化到系统托盘继续运行；开机自启（可选）；单实例运行；低 CPU / 内存占用 |
| F7 | 悬浮窗 | 置顶小窗显示「今日待办数量」（未完成 / 总数）；可拖动、位置记忆、可开关；单击悬浮窗唤起并聚焦主界面 |
| F8 | 统计 | 按 天 / 周 / 月 统计已完成事项数量与明细；趋势图、按标签分布、完成率 |
| F9 | 外观 | 浅色 / 深色 / 跟随系统 三种主题 |

### 1.2 非功能目标（初定，SRS 阶段细化）

| 指标 | 目标值 |
|---|---|
| 托盘常驻（主窗口已关闭，仅悬浮窗）总内存 | ≤ 80 MB |
| 主窗口打开时总内存 | ≤ 150 MB |
| 空闲 CPU 占用 | ≈ 0%（无轮询，事件/定时器驱动），平均 < 0.5% |
| 冷启动到可交互 | ≤ 1.5 s |
| 提醒准时性 | 误差 ≤ 5 s；休眠唤醒后补发错过的提醒 |
| 安装包体积 | ≤ 15 MB |
| 支持平台 | Windows 10/11（主要）；macOS、Linux（次要，架构上保持可移植） |

## 2. 技术选型

### 2.1 框架选择：Tauri 2（推荐）vs Electron

| 维度 | Tauri 2 | Electron |
|---|---|---|
| 内存占用（空窗口） | ~30–60 MB（复用系统 WebView2） | ~120–200 MB（内置 Chromium + Node） |
| 安装包体积 | ~5–10 MB | ~80–150 MB |
| 后台常驻能力 | Rust 主进程极轻，可销毁 WebView 仅留托盘 | Node 主进程常驻，基础占用高 |
| 托盘 / 通知 / 自启 / 单实例 | 官方插件齐全 | 内置 API 齐全 |
| 生态成熟度 | 主流且快速增长 | 最成熟 |
| 开发语言 | 前端 TS + 后端 Rust | 全 TS |

**结论：采用 Tauri 2。** 需求中「低 CPU 和内存占用常驻后台」是硬性目标，Tauri 在这一点上明显优于 Electron，同时仍是主流跨平台框架，UI 层同样使用 Web 技术。若团队不便引入 Rust，可退回 Electron 方案，前端代码基本可复用（见 §3 的分层设计）。

### 2.2 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 桌面框架 | Tauri 2 | 多窗口、托盘、插件体系 |
| 后端语言 | Rust（stable） | 数据访问、提醒调度、系统集成 |
| 前端框架 | React 18 + TypeScript + Vite | |
| UI 样式 | Tailwind CSS + shadcn/ui（Radix） | CSS 变量实现主题，`dark` class 切换深色模式 |
| 状态管理 | Zustand + TanStack Query | 轻量；Query 负责与后端命令的数据同步 |
| 图表 | Recharts（或按需引入 ECharts） | 统计模块 |
| 数据存储 | SQLite（rusqlite，WAL 模式） | 本地单文件，存于用户数据目录 |
| 循环规则 | RFC 5545 RRULE 子集（`rrule` crate） | 便于未来与日历互通 |
| 系统集成插件 | `tauri-plugin-notification` / `-autostart` / `-single-instance` / `-window-state` / `-store` | 通知、自启、单实例、窗口状态、设置 |
| 测试 | Rust：`cargo test`；前端：Vitest + Testing Library；E2E：WebdriverIO + tauri-driver | |
| 质量 | ESLint + Prettier、clippy + rustfmt、Husky + commitlint | |
| CI/CD | GitHub Actions：lint / test / 多平台构建 / Release 打包 | |
| 原型设计 | ui-ux-pro-max 插件 | 设计系统 + 高保真 HTML 原型 |

## 3. 架构设计（概要）

```
┌──────────────────────────── Tauri App ────────────────────────────┐
│  WebView: 主窗口 (React)            WebView: 悬浮窗 (极简页面)      │
│   ├─ 待办列表 / 编辑                  └─ 今日待办数 · 点击唤起主窗口 │
│   ├─ 标签树 / 标签管理                                              │
│   ├─ 统计                                                          │
│   └─ 设置                                                          │
│            ▲  invoke(commands) / listen(events)  ▼                │
│  Rust Core                                                        │
│   ├─ repo:     SQLite 仓储（todos / tags / reminders / logs）       │
│   ├─ scheduler: 提醒调度器（最小堆 + 单个 tokio 定时器，无轮询）    │
│   ├─ recurrence: 循环实例生成                                       │
│   ├─ stats:    统计聚合查询                                         │
│   ├─ tray:     托盘图标与菜单                                       │
│   └─ notifier: 系统通知封装                                         │
└───────────────────────────────────────────────────────────────────┘
```

### 3.1 关键设计要点

- **低占用常驻**：关闭主窗口时 *销毁* 主 WebView（而非隐藏），仅保留 Rust 核心 + 托盘 + 可选悬浮窗；重新打开时再创建。悬浮窗页面不引入 React 主包，单独极简入口。
- **提醒调度**：所有未触发提醒放入按触发时间排序的最小堆，只挂一个睡到最近触发点的定时器；数据变更时重算。监听系统休眠/唤醒与时钟变更，唤醒后补发错过的提醒。
- **循环事项**：事项保存 RRULE；勾选完成时写入完成记录并按规则生成下一次实例（"完成即生成下一条"模型），统计以完成记录为准。
- **多级标签**：`tags(id, parent_id, name, color, sort, path)`，`path` 为物化路径（如 `/1/4/9/`）便于"含子标签"查询；`todo_tags` 多对多关联。
- **今日待办数**：后端维护计数，在数据变更与跨零点时通过事件推送给悬浮窗与托盘提示，悬浮窗不自行轮询。
- **深色模式**：设计令牌以 CSS 变量定义两套取值；设置为"跟随系统"时监听 `prefers-color-scheme` 与 Tauri 主题事件。
- **分层可移植**：前端只依赖一层 `api/` 适配器调用后端；若改用 Electron，仅需替换该适配器与后端实现。

### 3.2 数据模型（初稿，SRS/设计阶段定稿）

| 表 | 主要字段 |
|---|---|
| `todos` | id, title, note, due_date, due_time, all_day, rrule, status, completed_at, priority, sort, created_at, updated_at, deleted_at |
| `tags` | id, parent_id, name, color, sort, path |
| `todo_tags` | todo_id, tag_id |
| `reminders` | id, todo_id, offset_minutes / fire_at, fired_at, snoozed_until |
| `completion_logs` | id, todo_id, occurrence_date, completed_at（统计数据源） |
| `settings` | key, value |

## 4. 阶段计划

整体采用"文档先行 + 原型确认 + 迭代开发"的方式，共 8 个阶段，预计约 12 周（单人全职估算，可按实际人力调整）。

| 阶段 | 名称 | 周期 | 主要产出 |
|---|---|---|---|
| P0 | 项目启动 | 第 1 周（前半） | 仓库、规划文档、目录结构、协作规范 |
| **P1** | **软件需求规格说明书（SRS）** | 第 1–2 周 | `docs/srs/SRS.md` |
| **P2** | **界面原型设计（ui-ux-pro-max）** | 第 3–4 周 | 设计系统 + 全页面高保真原型（浅/深色） |
| P3 | 技术设计 | 第 4–5 周 | 架构设计、数据库设计、接口定义、技术验证 Demo |
| P4 | 开发迭代 1：基础能力 | 第 5–7 周 | 待办 CRUD、勾选完成、时间设置、标签与标签管理、深色模式 |
| P5 | 开发迭代 2：系统能力 | 第 8–9 周 | 循环、提醒与系统通知、托盘常驻、自启、悬浮窗 |
| P6 | 开发迭代 3：统计与打磨 | 第 10 周 | 统计模块、设置页、性能优化、可访问性 |
| P7 | 测试与发布 | 第 11–12 周 | 测试报告、性能报告、安装包、v1.0.0 Release |

### P0 项目启动

- [ ] 初始化 git 仓库，关联远程 `https://github.com/AhDaii/XTodoY.git`
- [ ] 编写 README、项目规划（本文档）、`.gitignore`
- [ ] 约定分支模型与提交规范（见 §6）
- [ ] 建立 GitHub Issues / Milestones，与下列阶段一一对应

**出口标准**：仓库可访问，规划文档评审通过。

### P1 软件需求规格说明书（SRS）

参照 IEEE 29148 / IEEE 830 结构编写，产出 `docs/srs/SRS.md`。

- [ ] 1 引言：目的、范围、术语定义（待办、实例、循环规则、提醒、标签路径等）、参考资料
- [ ] 2 总体描述：产品视角、用户特征、运行环境、约束、假设与依赖
- [ ] 3 功能需求：F1–F9 逐条展开，每条包含 编号 / 描述 / 输入 / 处理 / 输出 / 优先级（MoSCoW）/ 验收标准
  - 重点澄清：循环事项的完成语义、逾期处理、提醒在关机/休眠期间的补发策略、删除父标签时子标签与事项的处理、"今日待办"的统计口径（是否含逾期）、周起始日（周一/周日）
- [ ] 4 外部接口需求：用户界面（页面清单与交互概述）、系统通知、托盘、文件系统
- [ ] 5 非功能需求：性能（§1.2 指标）、可靠性（数据不丢失、崩溃恢复）、可用性、可移植性、安全与隐私（纯本地存储）
- [ ] 6 数据需求：概念数据模型、数据保留与导入导出（JSON 备份）
- [ ] 7 用例与用户故事：用例图、主要用例描述
- [ ] 附录：需求追踪矩阵（需求 → 原型页面 → 测试用例）

**出口标准**：SRS 评审通过并打标签 `srs-v1.0`；之后需求变更走变更记录。

### P2 界面原型设计（使用 ui-ux-pro-max 插件）

基于 SRS 第 4 章页面清单，使用 **ui-ux-pro-max** 插件完成设计系统与高保真原型，产出放在 `design/`。

1. **设计方向与设计系统**（ui-ux-pro-max 检索风格 / 配色 / 字体搭配）
   - [ ] 确定视觉风格（建议：简洁、专注、低干扰的效率工具风格）
   - [ ] 输出设计令牌：色板（浅色 + 深色两套语义色）、字体与字号阶梯、间距、圆角、阴影、动效时长
   - [ ] 产出 `design/design-system.md` 与 `design/tokens.css`（可直接被前端复用）
2. **页面原型**（每页均提供浅色与深色两版）
   - [ ] 主界面：侧边栏（今天 / 计划 / 全部 / 已完成 / 标签树）+ 待办列表（单选框、标题、时间、循环与提醒图标、标签胶囊）
   - [ ] 待办新建 / 编辑面板：标题、备注、日期时间、循环规则选择器、提醒设置、标签多选
   - [ ] 标签管理：树形结构、拖拽排序与改层级、颜色、重命名、合并、删除确认
   - [ ] 统计页：日 / 周 / 月 切换、完成趋势图、标签分布、完成明细列表
   - [ ] 设置页：主题、开机自启、悬浮窗开关、默认提醒、周起始日、数据备份
   - [ ] 悬浮窗：今日待办数量（多种状态：有待办 / 全部完成 / 悬停）
   - [ ] 托盘菜单与系统通知样式（含"完成""稍后提醒"操作按钮）
   - [ ] 空状态、加载、错误提示等状态页
3. **交互与评审**
   - [ ] 以可点击的 HTML 原型串联主流程（`design/prototype/index.html`），在浏览器中走查
   - [ ] 用 ui-ux-pro-max 的 UX 准则做一轮检查：可访问性对比度（浅/深色均达 WCAG AA）、键盘操作、焦点状态、动效克制
   - [ ] 根据评审意见修订，回填 SRS 需求追踪矩阵

**出口标准**：全部页面原型（浅/深色）评审通过，设计令牌冻结为 `design-v1.0`。

## 6. 版本管理规范

- **远程仓库**：`https://github.com/AhDaii/XTodoY.git`
- **分支模型**：
  - `main`：稳定版本，仅通过 PR 合入，每次发布打 tag（`v1.0.0`）
  - `develop`：日常集成分支
  - `feature/<模块>`、`fix/<问题>`、`docs/<文档>`：从 `develop` 切出，完成后 PR 合回
- **提交规范**：Conventional Commits，例如 `feat(todo): 支持循环事项`、`docs(srs): 补充提醒补发需求`
- **阶段标签**：`srs-v1.0`、`design-v1.0` 等文档里程碑同样打 tag，便于追溯
- **Issue 管理**：每个阶段对应一个 Milestone，任务拆为 Issue，PR 关联 Issue

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| WebView2 多进程导致内存高于预期 | 常驻指标不达标 | 关闭即销毁主窗口；悬浮窗极简入口；P3 Spike 实测，必要时悬浮窗改为原生绘制 |
| Windows 通知在专注助手/勿扰模式下被屏蔽 | 用户错过提醒 | 设置页提示；可选应用内提醒弹窗作为补充渠道 |
| 休眠、关机期间提醒丢失 | 提醒不可靠 | 唤醒/启动时扫描错过的提醒并补发（合并通知） |
| 循环规则与时区/夏令时边界问题 | 时间错乱 | 统一以本地时区规则计算 + 边界单元测试 |
| 团队 Rust 经验不足 | 进度延迟 | 后端逻辑保持精简；前端 `api/` 适配层保留切换 Electron 的可能 |
